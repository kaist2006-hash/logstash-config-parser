# 재업로드 자료 재검증 — 2026-09-12

## 목적

사용자가 다시 제공한 카드사 전문 묶음과 두 원시로그를 기준으로 현재 `docs/card.conf` 구현이 같은 규격/로그를 대상으로 하는지 확인하고, 국민 IC / 롯데 MS 결과를 다시 독립 검증했다.

이 확인은 `bgf.conf` 설정을 복제하는 작업이 아니다. BGF에서 검증된 운영 패턴 중 **conf는 수집/라우팅을 담당하고, 상세 전문 파싱은 외부 Ruby + JSON 규격으로 분리하며, 규격은 register 시 한 번만 로드하는 구조**만 참고한다.

## 현재 구조

- `card.conf`: 기존 거래 로그 선택, `target_alias` 라우팅, Elasticsearch 출력 유지
- `card_detail_parser.rb`: ISO8583 계열 공통 파싱 엔진
- `card_detail_specs.json`: 카드사/IC·MS/통합별 규격 및 보류 사유
- 상세 결과는 `[card_detail]` namespace에만 추가
- 원본 `message`, `a_header`, `b_body`, `target_alias`는 상세 파서가 변경하지 않음
- JSON은 이벤트마다 읽지 않고 Ruby `register`에서 1회 로드/검증/컴파일
- 미정의/충돌 필드는 뒤 필드의 오프셋 오파싱을 막기 위해 중단 처리

## 대상 프로파일

| 카드사 | 프로파일 |
|---|---|
| 국민 | `kb_ic`, `kb_ms` |
| 농협 | `nh_ic`, `nh_ms` |
| 롯데 | `lotte_ic`, `lotte_ms` |
| 삼성 | `samsung_ic`, `samsung_ms` |
| 신한 | `shinhan_ic`, `shinhan_ms` |
| 우리 | `woori_sum` |
| 하나 | `hana_sum` |
| 현대 | `hyundai_ic`, `hyundai_ms` |

현재 실제 원시로그가 있는 `kb_ic`, `lotte_ms`만 기본 상세 파싱 활성화 상태다. 나머지는 문서 기반 규격 초안이 존재하지만 실로그 검증 전이므로 비활성화 상태를 유지한다. 이는 기존 card.conf 수집/라우팅/저장을 중단한다는 의미가 아니라 새 상세 파싱만 안전하게 gate하는 것이다.

## 재업로드 전문 문서 대조

재업로드된 카드사 전문 묶음의 국민/농협/롯데/삼성/신한/우리/하나/현대 원본 파일은 현재 `card_detail_specs.json`의 `sources`에 기록된 파일명과 SHA256 기준으로 동일한 원본 세트임을 확인했다.

따라서 동일 자료만으로 이미 `blocked` 처리한 충돌 필드를 추정값으로 해제하지 않는다. 대표 확인 필요 항목은 다음과 같다.

- 롯데 MS: 실로그 F57/F61이 제공 20211021 문서에 없음
- 롯데 IC: F35 길이/인코딩 모드, F145 문서 오기
- 농협 IC/MS: F118 총길이 표기 충돌
- 삼성 MS: F90/F127 거래별 형식 확인 필요
- 삼성 IC: F49 문서 간 길이 충돌
- 신한 IC: F120 length prefix 설명 충돌
- 하나 통합: F52 길이 표기 충돌
- 현대 MS: F90 취소전문 거래별 original data 확인 필요
- 우리 통합: TCP/UserArea 포함 위치는 실로그 확인 필요

## 국민 IC 전체 재검증

원시파일: `GICNB_X25A_P01.06242025.12.log`

| 항목 | 건수 |
|---|---:|
| 물리 행 | 453,297 |
| 기존 card.conf 거래 선택 대상 | 302,191 |
| 기존 조건에서 제외 | 151,106 |
| `ok` | 151,241 |
| `warning` | 150,950 |
| `partial` | 0 |
| `failed` | 0 |
| frame complete | 302,191 |

경고도 기존 결과와 동일하게 재현됐다.

- F60 문서 상한(4 bytes)보다 긴 실로그: 150,475
- F55 문서 상한보다 긴 실로그: 107,814
- 문서 기본 ISO header와 다른 header: 2

경고 이벤트도 전문 경계와 선택 필드/TLV 구조는 끝까지 해석됐다. 문서와 실로그의 차이를 숨기기 위해 상한을 임의로 수정하지 않는다.

## 롯데 MS 전체 재검증

원시파일: `GCLTC_X25A_P01.06152025.12.log`

| 항목 | 건수 |
|---|---:|
| 물리 행 | 51,818 |
| 기존 card.conf 거래 선택 대상 | 51,766 |
| 기존 조건에서 제외 | 52 |
| `ok` | 23,989 |
| `warning` | 0 |
| `partial` | 24,913 |
| `failed` | 2,864 |

부분/실패 사유도 기존 결과와 동일하게 재현됐다.

| 사유 | 건수 |
|---|---:|
| 미정의 F57 | 20,830 |
| 미정의 F61 | 2,145 |
| F35 본문 부족 | 1,915 |
| 외곽 text envelope 불완전 | 2,864 |
| 파싱 후 trailing bytes | 20 |
| F49 숫자값 오류 | 3 |
| F55 길이 prefix 오류 | 3 |
| 기록 len과 실제 본문 길이 차이 | 23,875 |

`RESPDATA` 8 bytes는 현재 파서와 동일하게 응답 접두어로만 처리했다. 그 외 차이를 임의로 보정하거나, F57/F61 길이를 일반 ISO8583 관례로 추정해 뒤 필드를 맞추지 않았다.

## 결론

1. 현재 `card.conf -> card_detail_parser.rb -> card_detail_specs.json` 구조는 사용자가 요구한 외부 Ruby/JSON 참조 방식과 운영 성능 방향을 이미 반영하고 있다.
2. 재업로드 문서는 현재 specs의 원본 세트와 동일하므로 14개 프로파일 정의를 새로 갈아엎을 이유가 없다.
3. 국민 IC는 제공 원시로그 전체에서 구조 검증을 다시 통과했다.
4. 롯데 MS는 제공 문서 자체에 F57/F61이 없고 일부 원시로그가 잘려 있어 현재 자료만으로 전체 성공 처리할 수 없다.
5. 나머지 카드사는 문서 기반 설정은 유지하되 실로그가 도착하는 순서대로 `blocked`/거래별 변형을 검증한 뒤 상세 파싱을 활성화한다.

운영 반영 시에는 `README.md`의 gate와 기존 `validation/REPORT.md`를 함께 확인한다.
