# 1차 검증 결과 — 2026-09-12

## 결론

**국민 IC는 제공 로그 전체의 프레임·선택 필드·TLV 구조 검증을 통과했습니다. 롯데 MS는 일부만 정상 완료되므로 전체 정상 파싱 완료로 판단할 수 없습니다.** 문서 차이 경고와 부분 실패를 숨기지 않은 1차 설정 후보입니다.

| 대상 | 거래 로그 수 | ok | warning | partial | failed |
|---|---:|---:|---:|---:|---:|
| 국민 IC | 302,191 | 151,241 | 150,950 | 0 | 0 |
| 롯데 MS | 51,766 | 23,989 | 0 | 24,913 | 2,864 |
| 합계 | 353,957 | 175,230 | 150,950 | 24,913 | 2,864 |

국민은 warning을 포함한 302,191건 모두 `frame_status=complete`입니다. 롯데는 정상 23,989건만 complete이며 나머지를 임의 복구하지 않았습니다. `warning`은 문서 규격과 완전히 같다는 뜻이 아닙니다.

## 실행과 대조 방법

- Elasticsearch/Beats 연결 및 저장 테스트는 사용자 요청 범위에서 제외했습니다.
- 공식 Logstash 8.17.6 Windows 배포본과 제공 SHA512를 대조했습니다. bundled JDK 21.0.7, JRuby 9.4.9.0, **실제 `LogStash::Event`**를 사용했습니다. Event 모조 객체 테스트가 아닙니다.
- 운영 conf 후보의 `--config.test_and_exit` 검사를 수행했습니다. Ruby 스크립트와 JSON register도 실행됐습니다. 자체 내장 DSL test 수 0 표시는 아래 별도 실행 검증 건수와 무관합니다.
- 합성 입력 계약 25건 + namespace 충돌/설정 오류 2건 = **27건 통과**.
- 원시 로그에서 MTI/bitmap 조합별 **28개 표본, 455개 필드값**을 Python 별도 바이트 오프셋 계산 결과와 대조: 전부 일치. JSON 규격 파일을 그대로 읽어 기대값을 만든 것은 아닙니다. 실제 원문을 담은 golden fixture는 공개 묶음에서 제외했습니다.
- 두 파일 전체를 **1 thread / 4 threads**로 같은 파서 인스턴스에 각각 재생했습니다. 건수·진단·전체 상세 결과의 순서 독립 SHA256 sum/xor가 모두 동일했습니다. 이는 파서 공유 상태 검증이며 Logstash 전체 pipeline 부하 시험이라고 부르지 않습니다.
- 각 실행 모두 이벤트 유실/복제 0, message 변경 0, target_alias 변경 0, 예기치 않은 파서 예외 0.
- 최종 실행 소요: 단일 153.605초, 4 threads 64.461초. 파일 읽기·Event 생성·결과 digest 계산 포함, 로컬 재생 측정일 뿐 운영 처리량이나 권장 worker 수를 확정하는 근거가 아닙니다.

원본 물리 행은 국민 453,297행, 롯데 51,818행입니다. 기존 conf의 거래 로그 선택 조건에서 제외되는 행은 각각 151,106 / 52행입니다. 이 행을 새 파서가 유실한 것으로 계산하지 않았습니다. 심하게 잘린 롯데 시작 행 2,864건은 거래 선택 조건에 포함되므로 실패로 집계했습니다.

## 국민 IC 문서와의 차이

| 경고 | 발생 건수 | 해석 |
|---|---:|---|
| F60 문서 최대 길이 초과 | 150,475 | 문서는 8 BCD=4바이트. 실제 prefix는 byte 수이고 5바이트 사례 존재 |
| F55 문서 최대 길이 초과 | 107,814 | 문서 MCHIP 상한과 다른 TLV payload 길이. 실제 TLV 구조/경계 검사는 통과 |
| ISO 헤더 문서와 다름 | 2 | 문서 ISO023400053 외 ISO023400075 관측 |

경고는 한 이벤트에 중복될 수 있으므로 합산하면 warning 이벤트 수보다 큽니다. F60은 실로그 관측에 따라 prefix 단위를 bytes로 명시하고 상한 5, 문서 상한 4를 따로 보관했습니다. F55는 1byte prefix로 표현 가능한 범위를 제한하되 문서 상한 초과 경고를 남깁니다. 문서를 수정하거나 모든 차이를 표준으로 단정하지 않았습니다.

## 롯데 MS 실패·부분 해석 사유

| 사유 | 발생 건수 |
|---|---:|
| 미정의 F57에서 중단 | 20,830 |
| 미정의 F61에서 중단 | 2,145 |
| F35 본문 부족 | 1,915 |
| 외곽 `data[...] len[...]` 기록 미완성 | 2,864 |
| 파싱 이후 남는 바이트 | 20 |
| F49 숫자값 오류 | 3 |
| F55 길이 prefix 오류 | 3 |

오류도 한 이벤트에 여러 개 존재할 수 있습니다. 별도로 기록 len과 본문 바이트 수 불일치가 23,875건 있었습니다. `RESPDATA` 8바이트는 실제 로그 접두어로 처리하되, 그 밖의 8바이트 차이를 무조건 빼거나 본문을 임의 절단하지 않았습니다.

필요한 후속 자료는 **실제 운영 버전의 롯데 MS F57/F61 포함 규격**, 그리고 잘린 본문의 **온전한 원시/HEX 기록본**입니다. 지금 자료만으로 손상된 뒤쪽 값을 만들어낼 수 없습니다. 제공된 20211021 문서만으로 전체 정상 파싱을 강행해서는 안 됩니다.

## 나머지 프로파일의 상태

나머지 12개 프로파일은 문서 기반 길이 설정 초안이며 비활성화입니다. 모든 필드의 업무별 하위 해석이 완성됐다는 뜻이 아닙니다. 예를 들어 농협 F118 총길이, 삼성 IC F49, 하나 F52, 롯데 IC F35 길이 모드와 F145 오기, 신한 IC F120 prefix 등은 확인이 필요합니다. `kind=blocked` 및 notes에 사유를 남겼습니다. 실제 표본이 오면 해당 MTI/비트 조합부터 검증하고, 충돌 필드를 해소한 뒤 활성화해야 합니다.

## 검증하지 않은 것

전체 업무별 필수값 규칙, 민감 필드의 금융 업무 유효성, 암호·PIN 검증, 한글 자유문 전체 디코딩, 승인/취소 상관관계, 다른 카드사 원시 로그는 검증하지 않았습니다. 기본 내보내기는 비민감 운영 필드 위주이며 전문 모든 값을 ES 필드로 복제하는 설계가 아닙니다.

전체 프로세스의 파일 input 재생은 이 Windows 실행 환경의 `.lock` 접근 거부로 중단됐습니다. Logstash 코드나 잠금 기능을 변경하지 않았고, 파서 전체 원시 로그 재생은 실제 동일 버전의 RubyUtil/Event 런타임에서 완료했습니다. 사용자 요청 범위인 원시 로그→Ruby/JSON 검증은 이 방식으로 수행했으며, 외부망에서 내부 ES에 연결하는 시도는 하지 않았습니다.

세부 집계는 `core-final-w1.json`, `core-final-w4.json`, 합성 검증은 `contracts-result.json`, 표본 대조는 `golden-result.json`을 확인하세요.
