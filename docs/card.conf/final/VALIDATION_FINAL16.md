# FINAL16 검증 결과 — 롯데·농협 오분류 및 삼성 입력 식별

이번 수정은 사진과 실로그에서 확인한 두 파싱 오분류를 보완하고, 삼성 화면에 BC 원본이 들어간 문제를 구분합니다. Filebeat euc-kr, 최소 진단 출력, 카드사별 독립 규격, fallback의 공통 전용 출력은 유지합니다.

## 농협 MS: 짧은 비정상 로그가 아니라 다른 망관리 배치

사진의 0800/0810은 NHCARD 사용자영역과 ISO000000000 헤더를 갖습니다. 문서의 통신망관리 sheet는 94바이트와 bitmap 822000000A000000/0400000000000000을 정의하지만, 실로그는 ISO 기준 211바이트(사용자영역 포함 220, 요청 길이 접두부 포함 224)의 다른 배치를 사용합니다. 실제 bitmap은 F23C66812EC098100000000000000400입니다.

기존 파서는 이 bitmap을 거래 필드 배열로 읽어 DE41 절단 또는 F118 길이 문제를 만들었습니다. **142건을 심한 절단으로 설명한 이전 판단은 잘못이었습니다.** 실제 입력에는 앞 60/뒤 80바이트 예약 공백 사이에 전송일시 14자리·추적번호 6자리·망관리코드 3자리가 있습니다. ISO 기준 위치 108/122/128이며 186건 모두 날짜가 유효하고 코드가 301입니다.

network_common_fallback은 헤더·MTI·bitmap·사용자영역·길이 접두부·예약 공백을 확인한 뒤 기존 해당 카드사의 DE7/11/70 디코더로 이 세 값만 추출합니다. 조건을 만족하지 않는 메시지를 일괄 승격하지 않습니다. 공통 값이 부족하거나 손상되면 기존 판정으로 error이며, 충분히 읽은 공통 값만 있으면 fallback입니다. 전체 입력 message는 유지합니다. 알려진 망관리 구간 뒤의 로깅 버퍼를 거래 필드로 해석하지 않습니다.

실로그 186건 모두 source 원문 구간과 출력 세 값이 일치했습니다. FINAL15의 error 142건 → fallback, 기존 fallback 44건도 잘못 읽었던 거래 공통값 대신 실제 망관리 세 값으로 교정했습니다. 농협 MS 전체 **10,296건: ok 9,720 / fallback 576 / error 0**입니다. warnings에 network_layout_common_only가 표시됩니다.

## 롯데 MS: 존재하는 헤더를 허용하지 못한 문제

사진과 일치하는 4건은 ISO023400050 + 0420인데 설정은 ISO023400053만 허용했습니다. 헤더가 없는 것이 아니었습니다. 이 조합을 별도 common_header_fallback으로 등록해 공통 DE3~49만 읽고 상세 전에 중단합니다. 4건 모두 공통필드 + fallback이며 warnings는 header_variant_common_only입니다.

추가 점검에서 국민 IC의 ISO023400075 + 0200 두 건도 독립적인 Binary 접두부 규칙으로 같은 범위의 공통 fallback을 보완했습니다. 기본 헤더의 상세 파싱과 다른 카드사·IC/MS 프로필은 유지합니다.

롯데 후보 시험의 남은 error 5건은 거래 봉투가 없는 CSV 진단행입니다. 기존 card.conf 앞단에서 제외되는 것을 실제 파이프라인으로 확인했습니다. 따라서 사진의 4건과 이 진단행 5건은 같은 종류로 집계하면 안 됩니다.

## 삼성 MS: 사진의 원본은 BC MS

사진의 gateway는 GINST_0005_D01이고 본문은 BCB/EPT/HDRREQPOLL입니다. 사진의 문서 13,456건도 기존 BC MS의 거래/제어 개수와 일치합니다. 예전 zip의 win_ms와 bcc_ms는 SHA256까지 같은 파일입니다.

| 원본 | gateway | 물리 줄 수 | SHA256 |
|---|---|---:|---|
| 예전 win_ms = bcc_ms | GINST_0005_D01 | 22,728 | 459dfcaf3cd803a0b17fe2d704cafbff65250c0fc414ac271e4bc8f33e588be2 |
| 나중에 제공한 실제 삼성 win_ms/win_ms | GINST_0005_A01 | 113,192 | bd71e484b9ea3bb2b09f2b3736d29b6a927edec4785fe4d08cf946270e280dd1 |

같은 BC 원본을 samsung_ms로 지정하면 **13,456건 모두 error**, bcc_ms로 지정하면 **ok 5,776(구조 확인) + control 7,680, error 0**으로 재현했습니다. 삼성 파서의 필드 누락으로 볼 사례가 아니라 입력 원본과 서비스 지정의 불일치입니다. BC 구형 레코드의 내부 업무 필드 규격 미확정 상태는 유지합니다.

실제 삼성 원본을 최종 파일로 다시 전량 재생한 결과 **ok 47,970 / fallback 65,166 / error 56**입니다. 정상 전문에는 공통/상세 값이 출력되고, 56줄은 봉투가 없는 조각입니다. 확인본 SAMSUNG_MS_GINST_0005_A01.log는 새 삼성 원본과 바이트·SHA256이 동일합니다. 원문 확인본은 사용자 로컬에만 제공하며 설정 ZIP/GitHub에 포함하지 않습니다. 삼성 테스트는 A01인 새 수집 이벤트를 확인해야 합니다. 설정 교체만으로 기존 BC 데이터가 삼성 원문으로 바뀌지는 않습니다.

- 기존 dissect/grok/서비스 라우팅까지 포함한 파이프라인 **197행 입력 → 기대한 192건 출력**, CSV 진단 5행 제외. 농협 186·롯데 4·실제 삼성 요청/응답 2건을 확인했고 error 태그는 없습니다.
- 비교 가능한 14개 서비스의 승인 요청/응답 1,400쌍에서 금액·가맹점번호·통화 차이는 없었습니다. BC 두 서비스는 비교 조건을 충족하지 못해 해당 시험 통과로 세지 않습니다.
- 농협 금융 전문의 문서 뒤 rest 처리 **56,692건 / 42,004,838바이트**는 유지했습니다. 망관리 호환 배치는 공통 전용 fallback이며 거래 상세/rest를 만들지 않습니다.
- JSON 1회 로드·컴파일·동결, 카드사 직접 선택, 상수 접두부·예약 공백 사전 준비, 이벤트당 파일/네트워크 I/O 없음 등 기존 최적화를 유지했습니다. 진단 기본값 minimal로 parser_version·bitmap·바이트 카운터를 숨깁니다. 같은 712개 실로그 회귀 표본의 card_detail 크기는 full 654,047 → minimal 351,936바이트(46.19% 감소)였습니다. 운영 저장량/처리량 개선율이 아닙니다.

## 남은 범위

error 111건에는 BC IC의 별도 구형 ISO 형식 42건과 봉투/헤더 미확인 후보 69건이 남습니다. BC 문서는 BCINTMSG0001을 신규 통합, ISO023400053을 과거 MS로 구분하고 금액 길이 확장을 명시합니다. 0540/0550의 구형 본문에 현재 통합 필드를 적용해 값을 추측하지 않았습니다. 이 미지원 상태를 비정상 거래라고 단정할 수 없습니다. 이전의 “117건 모두 헤더 없음”, “농협 142건은 심한 절단” 설명은 이번 분석으로 정정합니다.

BC MS의 ok 5,776은 고정 레코드 구조 확인으로 내부 업무 필드 완료가 아닙니다. 롯데 IC는 제공 ASCII 경로를 검증했으며 별도 최신 binary IC와 미관측 필드/MTI 조합까지 완료한 것은 아닙니다. 실 Filebeat → Elasticsearch 운영 종단 시험은 수행하지 않았습니다. CP949 입력 복원과 실제 Logstash 파이프라인까지 검증했습니다.

카드사별 위치/관측 수는 CARD_FIELDS_FINAL16.md, 입력 선택은 SERVICE_INPUT_GUIDE_FINAL16.md, 적용은 APPLY_GUIDE_FINAL16.md, 파일 해시는 MANIFEST_FINAL16.json을 확인하세요. 배포 설정과 공개 보고서에는 실제 거래 원문/값을 넣지 않았습니다.
