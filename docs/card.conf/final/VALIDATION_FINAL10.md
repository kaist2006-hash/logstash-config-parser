# 카드 파서 final10 검증 및 적용 안내

최종 정리: 2026-10-30. 파서/JSON 버전: `2026-10-18.final10`.
전체 실로그 재생은 2026-10-18에 완료했으며, 2026-10-30에는 배포 파일 일치 여부와 추가 분류 계약을 확인했다.

## 변경 내용

농협 IC·MS 프로필에만 `allow_unparsed_rest: true`를 적용했다. 정의된 필드의 해석이 끝난 뒤 남은 payload는 `card_detail.rest` 한 필드에 대문자 16진수 문자열로 보존한다. `remaining_bytes`는 해당 원문의 바이트 길이다. 원문 바이트를 문자열 인코딩 때문에 잃지 않도록 HEX로 저장하며, HEX는 암호화가 아니다.

이 경우 앞부분에 업무 필드가 추출되고 별도의 파싱 오류가 없으면 `status=ok`로 분류한다. `warnings`에는 `unparsed_rest`가 남는다. 농협 IC의 F127 응답 생략 경고는 이 경우 함께 허용한다. 길이 접두부 오류·숫자값 오류 등 앞부분의 실제 오류가 있으면 `rest` 때문에 `ok`로 바뀌지 않는다. `ok`는 알려진 구간의 파싱과 후행 데이터 보존이 완료됐다는 뜻이며, `rest` 내부의 필드 구조가 해석됐다는 뜻은 아니다.

농협 이외의 프로필에는 이 허용값을 추가하지 않았다. 해당 카드사의 설명되지 않은 후행 데이터는 기존 `trailing_bytes` 오류로 유지한다. 카드사·서비스 규격은 각각 독립 정의한다.

## 전체 실로그 결과

Logstash 8.17.6 내장 JRuby와 실제 `LogStash::Event`에서 `register`에 `specs_path`만 전달하고 4개 워커로 재생했다. 대상은 제공된 15개 고유 로그의 전문 후보 이벤트다. `win_ms`는 `bcc_ms`와 바이트가 같은 중복 파일이므로 BC MS로만 사용했다. 삼성 MS 실로그는 없다.

총 1,152,346건. final9와 비교해 농협 IC 55,617건과 농협 MS 1,075건, 합계 56,692건만 `error`에서 `ok`로 변경됐다. 다른 카드사의 분류 건수와 기존 fallback 건수는 동일하다. 입력 `message`와 라우팅 메타데이터 변경은 모두 0건이다. 1,131,636건에서 업무 필드가 하나 이상 추출됐다.

`rest`로 보존한 원문은 합계 42,004,838바이트이며, HEX 값은 합계 84,009,676문자다. 재생 보고서에는 전문 원문이나 `rest` 값을 기록하지 않았다.

추가 계약 검증에서 다음을 확인했다.

- 짧은 동종 전문은 공통 필드와 `fallback` 태그를 유지한다.
- 잘못된 길이 접두부와 공통 필드가 없는 회복 실패는 `error`다.
- 농협 MS 및 F127 비트가 켜진 농협 IC 응답의 후행 바이트 `00 FF 20 58`이 정확히 `rest=00FF2058`로 보존되고 `ok`가 된다.
- 농협의 알려진 앞부분 필드가 잘못된 경우에는 후행 데이터가 있어도 `error`다.
- 국민 프로필의 설명되지 않은 후행 데이터는 계속 `error`다.

## 상태 해석과 남은 범위

`fallback`은 공통 필드를 확보한 같은 프로필의 절단/봉투 복구 등 회복 가능한 결과다. `error`는 현재 정의로 구조나 값을 확인하지 못한 상태이며 거래 거절 여부를 뜻하지 않는다. `control`은 확인된 제어·상태 전문으로 거래 상세 파싱 대상에서 분리한다. 공개 실패 태그는 `fallback`과 `error`만 사용하고 `ok`·`control`에는 해당 태그를 추가하지 않는다.

BC MS 5,776건의 `ok`는 BCB/BCA/EPT 레코드의 표식·방향·전체 길이 확인이다. 내부 업무 필드 offset 근거가 없어 상세 `fields`는 출력하지 않는다. 삼성 MS는 실로그가 없어 비활성이다. 롯데 IC는 제공된 ASCII 형태 로그로 검증했으며, 문서상의 바이너리 IC 형식은 검증하지 않았다.

농협 `rest` 내부 규격은 여전히 미확정이다. 최종 엑셀에 이 범위를 명시했으며, 추후 응답 레이아웃이 확보되면 별도의 필드 정의로 확장할 수 있다.

## 운영 적용과 최적화

기존 단일 Ruby 필터와 JSON 규격 방식은 유지한다. 규격 로드·검증·컴파일·freeze는 `register`에서 한 번만 수행하며 이벤트별 파일 읽기나 네트워크 호출은 없다. 기존 본문 상한, bitmap 수, 가변 필드 길이 및 TLV 범위 검사도 유지한다. 새 HEX 변환은 농협의 해당 후행 데이터가 존재할 때만 수행한다.

전체 재생은 280.401초, 테스트 하네스를 포함해 약 4,110건/초였다. 이는 해당 재생 환경의 측정치이며 운영 장비의 처리량 보증은 아니다. `rest`는 원문 데이터이므로 저장 용량이 증가하며, 운영 매핑에서 검색이 필요 없다면 색인 및 doc_values 제외를 검토할 수 있다.

RB·JSON을 동일한 `CARD_PARSER_DIR`에 아래 이름으로 배치한다.

```text
card_detail_parser.rb
card_detail_specs.json
```

사용자 지정 Ruby 블록은 그대로 사용할 수 있다.

```text
ruby {
  id => "card_detail_parser"
  path => "${CARD_PARSER_DIR}/card_detail_parser.rb"
  script_params => {
    "specs_path" => "${CARD_PARSER_DIR}/card_detail_specs.json"
  }
}
```

앞단 카드사별 `[@metadata][target_alias]` 라우팅, 멀티라인 처리 및 원본 `message` 보존은 기존 설정이 담당한다. 재시작 후 `card_detail.parser_version=2026-10-18.final10`을 확인한다. 운영 서버에서는 `bin/logstash -t -f card.conf`로 전체 파이프라인 설정 검사를 수행해야 한다. 작업 환경에서는 실제 Event/JRuby 재생을 통과했지만 전체 플러그인 초기화와 Filebeat→Logstash→Elasticsearch 종단 간 운영 검증은 포함하지 않았다.

## 엑셀 문서

기존 전체 공통필드 시트와 카드사별 시트·열 구조를 유지하고, 프로필별 결과·공통 필드·상세 필드·예외 구간을 구분했다. 반복 비고를 줄이고 농협 `rest`, BC MS 상세 미해석, 삼성 MS 실로그 없음 및 롯데 IC 검증 형식을 명시했다. JSON의 16개 프로필 전체 emit 정의와 엑셀 필드 목록의 일치 여부를 확인했다. 워크북 오류값 검색은 0건이다. 자동 렌더러가 종료되어 저장 파일의 스타일·셀 크기를 사용한 별도 미리보기로 검토했으며 실제 Excel 앱 화면 검증은 수행하지 않았다.
