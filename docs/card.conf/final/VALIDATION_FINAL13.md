# CARD FINAL13 삼성 MS 요청 포장 형식 보완

버전 `2026-10-30.final13`, 검증일 2026-10-30.

## 이전 검증 범위의 오류

기존 FINAL11/12 재생기는 `(get|put)(...)` 또는 대괄호 HEX 형태만 골랐다. 삼성 파일의 `put_msg_complete[...]` 56,568줄도 실제 ISO 요청 전문이지만 선택되지 않았다. 따라서 이전 삼성 MS error 0이라는 수치는 응답 get 56,568건에만 해당한다. 요청까지 모두 검증됐다는 의미로 사용할 수 없다.

삼성 원본 전체는 113,192줄이다. 요청 `put_msg_complete[...]` 56,568건, 응답 `get(data[RESPDATAISO...])` 56,568건, 두 포장/ISO 헤더가 없는 56줄이다. 요청 MTI는 0200 49,387 / 0420 6,937 / 0800 244이며 응답은 각각 0210/0430/0810이다.

## 수정 내용

삼성 MS transport에만 `completed_text_envelope: true`를 추가했다. Ruby는 `put_msg_complete[내용] linename[...]` 또는 linename이 없는 형태를 인식하고 포장을 제거한 뒤 CP949 역변환과 기존 삼성 필드 파싱을 수행한다. 닫는 포장이 없는 7,046건도 알려진 내용까지 복구하되 경고를 남긴다. `log_encoding=completed_text`, 방향 OUT으로 구분한다.

기존 get/put/HEX 처리는 유지한다. 카드사별 필드 정의·타입·길이와 농협 rest 정책을 변경하지 않았다. 삼성 요청의 F55/F127 오류를 임의로 정상 처리하거나 후행 버퍼를 새 rest 규격으로 추정하지 않았다. 전송 인코딩은 사용자 설정대로 Filebeat euc-kr / JSON CP949를 유지한다. 새 정규식은 시작 시 컴파일하고 해당 옵션은 삼성 MS만 사용한다.

## 삼성 파일 전체 재생 결과

EUC-KR 호환 CP949 디코딩/치환 입력을 실제 Logstash 8.17.6 JRuby/Event에 넣었다. 실제 Filebeat부터 연결한 시험은 아니다.

| 입력 구분 | 대상 | ok | fallback | error |
|---|---:|---:|---:|---:|
| 응답 get | 56,568 | 47,970 | 8,598 | 0 |
| 요청 put_msg_complete | 56,568 | 0 | 54,940 | 1,628 |
| 포장/ISO 없는 줄 | 56 | 0 | 0 | 56 |
| 전체 물리 줄 | 113,192 | 47,970 | 63,538 | 1,684 |

기존 FINAL12로 같은 전체 입력을 재생하면 요청 56,568건과 포장 없는 56건이 error로 나왔다. 전체의 약 절반이 오류인 현상을 재현했다. 해당 직접 재생에서 기존 원인 코드는 incomplete_text_envelope였다. 사용자가 운영에서 확인한 missing_iso_header/input_decoding_loss와 코드가 완전히 같다고 단정하지 않는다. 운영의 put 포장 형식은 새로 지원한 put_msg_complete[ISO…와 일치한다. 적용 후 새 버전과 log_encoding으로 실제 교체 여부를 확인한다.

모든 요청/응답 후보 113,136건에서 하나 이상의 업무 필드를 추출했다. fallback에도 이미 확인된 상세 필드가 포함될 수 있다. 요청 56,567건에는 CP949로 해석할 수 없는 바이트가 있었으며, 알려진 필드 파싱이 끝난 뒤 발생하는 손실이 대부분이다. 이런 버퍼의 원본 바이트와 의미를 추측해 복구하지 않으므로 요청을 모두 ok로 표시하지 않는다. 본문의 실제 카드 거래 정상 여부와 파서 상태는 별개다.

## 남은 error 1,684건

- ISO023400053/0200 요청 1,606건: F55 길이 3자리 위치가 공백이다. 현행 문서의 길이 표기와 맞지 않아 상세 파싱이 중단된다.
- 요청 20건: F127 길이 자리가 숫자가 아니다.
- 요청 1건: F32 길이가 현재 상한을 초과한다.
- 요청 1건: F56 길이 자리가 마스킹됐다.
- 포장/ISO 헤더 없는 56줄: 현재 규칙으로 업무 필드를 복구할 수 없다.

이 1,684건을 모두 비정상 거래라고 단정하지 않는다. 특히 구형 요청 1,606건을 규격대로 끝까지 파싱했다고 말할 수 없다. 정상으로 보이는 로그라 하더라도 문서와 맞지 않는 길이 위치는 별도 구형 규격/원문 상태 확인 대상이다. 이번에는 이를 숨기기 위해 error를 fallback/ok로 바꾸지 않았다.

## 검증 근거와 한계

- 삼성 전체 113,192줄을 FINAL12/FINAL13 및 바이트 보존 참조 경로로 각각 시험했다. 삼성 요청을 사전 선택에서 제외하지 않았다.
- 기존 응답 56,568건의 card_detail 전체(버전 제외)와 tags 차이 0건. 입력 message/라우팅 변경 0건.
- 기존 계약 17개, 새 포장 계약 6개 통과. 다른 15개 서비스에서 각 64건씩 960건을 FINAL12와 비교해 차이 0건. 다른 카드사 전체를 FINAL13으로 전량 재생했다는 의미는 아니다.
- 실제 요청/응답 헤더·MTI 조합과 조각에서 뽑은 68건을 실제 Logstash stdin/json_lines → Ruby(specs_path만 지정) → file 파이프라인에 넣었다. 직접 파서와 결과 차이 0건.
- 다른 15개 파일도 기존 제외 줄의 함수명·ISO·data 표식을 감사했다. 보고서는 EXCLUDED_INPUT_AUDIT.json에 있다. 표식이 있는 제외 줄을 모두 상세 파싱했다는 뜻은 아니다.
- core_replay.rb의 후보 선택에 put_msg_complete[를 추가해 같은 누락이 반복되지 않도록 했다. 참고 card.conf에도 해당 입력을 Ruby 앞에서 drop하지 않는 분기를 추가했다.

원본·결과의 카드번호나 업무 값은 검증 보고서에 포함하지 않았다. 파일의 전체 내용은 로컬 시험에서만 사용했다. 농협 F118/F124 경계 401건의 기존 문제는 이번 삼성 보완과 별개로 남아 있다.
