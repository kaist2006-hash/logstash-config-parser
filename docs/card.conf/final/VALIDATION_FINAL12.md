# CARD FINAL12 간소화·최적화 검토

> **삼성 검증 범위 정정:** FINAL11/12 비교의 삼성 MS 56,568건은 get 응답만 포함했다. put_msg_complete 요청 56,568건을 후보 선택에서 누락했다. 두 버전의 선택된 입력 결과가 같다는 검증은 유지되지만 삼성 전체가 검증됐다는 의미는 아니다. [FINAL13](VALIDATION_FINAL13.md)에서 전체 원문을 다시 시험하고 요청 포장을 보완했다.

버전: `2026-10-30.final12` · 검토일: 2026-10-30.

## 판단

기존 구조는 JSON을 시작 시 한 번 읽고 카드사 alias와 컴파일된 필드 배열로 처리하는 적절한 구조다. 이번에는 Ruby의 반복 분기와 이벤트마다 반복되던 작은 객체 생성을 정리했다. RB는 726줄/31,147바이트에서 713줄/30,424바이트로 줄었다. 줄 수나 파일 크기를 성능 지표로 사용하지 않는다.

JSON은 버전 문자열만 바꿨다. 16개 서비스·510개 DE 규격 정의와 필드 이름·형식·길이·추출 정책은 그대로다. 카드사별 독립 정의는 유지보수와 규격 변경 추적에 필요하다. 53,069바이트의 JSON을 이벤트마다 읽는 구조가 아니므로, 이를 축약하거나 카드사 간 상속·공유 규격으로 바꾸는 추가 복잡성을 넣지 않았다.

## 동일성 검증

Logstash 8.17.6의 실제 JRuby/Event와 공유 파서 4개 워커에서 1,208,914개 전문 후보를 FINAL11과 FINAL12에 각각 넣었다. 운영 조건인 euc-kr에 호환되는 CP949 디코딩/치환 문자열을 사용했다. 실제 Filebeat부터 Elasticsearch까지 연결한 시험은 아니다.

비교는 버전 문자열을 제외한 card_detail 전체(필드 값, rest, EMV, 오류·경고·오프셋·진단 값)와 tags를 대상으로 했다. 결과 불일치, tags 불일치, 원문/라우팅 변경, 버전 오류는 각각 0건이다. 상태별 건수는 모든 서비스에서 FINAL11과 같았다.

기존 계약 7개와 인코딩 계약 10개, 1,746개 바이트/봉투 경계값 비교를 통과했다. 실제 Logstash 파이프라인 4개 합성 이벤트도 `specs_path`만 지정해 통과했다. 정상·손실 fallback·명백한 헤더 오류·삼성 구형 공백 응답을 포함한다.

## 성능 표본

16개 서비스별 첫 64개 후보, 총 1,024건의 균등 표본으로 비교했다. 워밍업 후 단일 워커에서 회당 3,072건, 6회씩 순서를 바꿔 실행했으며 Event 생성도 포함했다.

FINAL11 중앙값 1.226초 / FINAL12 중앙값 0.981초다. 표본의 중앙 처리시간 변화는 19.94% 감소다. 이 표본은 실제 트래픽 비율이 아니며 운영 EPS나 최대 성능을 보장하지 않는다. 원시 측정치는 BENCHMARK.json에 있다.

## 적용과 기존 제한

RB와 JSON을 함께 FINAL12로 교체한다. Filebeat `encoding: euc-kr`과 Ruby의 `specs_path`만 넣는 설정을 유지한다. CP949 역변환, 손실 전 접두부의 fallback, 농협의 알려진 필드 파싱 완료 후 rest HEX 저장, error/fallback/control 정책과 필드 타입은 변경하지 않았다. JSON의 numeric은 숫자 내용 검증이며 타입 변환이 아니다.

이번 작업은 간소화와 동일성 검증이다. **농협 IC F118/F124 필드 경계 미해결 401건은 여전히 error다.** 농협의 파싱 완료 후 후행 바이트를 rest로 보관하는 처리와 별개다. 전체 error 535건을 모두 비정상 거래라고 단정하지 않는다.

BC MS의 ok 5,776건은 고정 레코드 표식·방향·길이 검증이며 내부 업무 필드는 출력하지 않는다. 삼성 MS 검증 자료는 0210/0430/0810 응답이며 요청·다른 MTI는 실로그 미검증이다. 삼성 F127은 길이 영역을 소비하지만 내부 항목을 개별 필드로 출력하지 않는다. 롯데 IC는 제공된 ASCII 형태를 검증했고 문서의 바이너리 IC 형태는 미검증이다.

최종 설정에 추가 축약이나 카드사 규격 통합은 필요하지 않다고 판단한다. 상세 출력·원문·분류를 유지하면서 반복 작업을 줄인 범위로 마무리했다.
