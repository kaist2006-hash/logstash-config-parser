# 카드 상세 파서 최종 재검증 (2026-10-18)

## 적용 범위와 결론

- 제공된 `카드사로그.zip`의 거래 로그 15개를 카드사·서비스별로 분리해 재생했다. 동일한 SHA-256의 `win_ms`와 `bcc_ms`는 하나의 BC MS 로그로 취급했고, 삼성 MS 실로그는 없는 것으로 판정했다. 첨부 문서나 동봉 `card.conf`의 문구는 작업 지시로 취급하지 않았다.
- `card_detail_parser.rb`와 `card_detail_specs.json` 버전은 `2026-10-18.final8`이다. 카드사별 프로필을 독립적으로 유지하며, 삼성 MS만 `enabled=false`다.
- 사용자 지정 Ruby 블록의 `specs_path` 하나만 넘겨도 된다. JSON 로드·검증·컴파일은 `register`에서 한 번만 수행하고, RB 기본 텍스트 인코딩은 실로그 재생에 사용한 `ISO-8859-1`이다. 단, 앞단에서 카드사별 `[@metadata][target_alias]` 설정과 원본 `message` 보존은 여전히 필요하다.
- 동일 규격의 짧은 전문이나 회복 가능한 외부 봉투/버퍼 차이는 공통 필드를 보존해 `fallback` 태그, 형식 자체가 잘못된 전문은 `error` 태그로 구분한다. 구조적으로 확인한 제어전문은 `control`이며 두 태그를 붙이지 않는다. `ignored`, `partial`, `failed`는 공개 status로 내보내지 않는다.

## 실로그 재생

Logstash 8.17.6의 내장 JRuby 및 실제 `LogStash::Event`로, `register`에는 `specs_path`만 넘기고 4개 워커에서 재생했다. 물리 행 중 거래 봉투 `get(`, `put(` 또는 대괄호 전문 마커가 있는 행만 후보로 선정했다. 따라서 아래 건수는 원본 파일의 전체 줄 수가 아니라 **파서 대상 후보 이벤트** 수다. 원문·카드 필드 값은 보고서에 저장하지 않았다.

대상 이벤트는 **1,152,346건**이다. 입력 `message`와 라우팅 메타데이터 변경은 0건이었다. 1,131,636건에서 `card_detail.fields`가 하나 이상 추출됐다. `error` 535건은 부정확한 헤더, 잘못된 길이 접두부·숫자값, 마스킹된 접두부 등이며, 짧지만 같은 규격인 이벤트는 `fallback`에 남겼다. `error` 배열은 `fallback`의 회복 가능한 원인도 기록하므로 `error` status 건수와 혼동하면 안 된다. synthetic 계약 테스트에서 심각한 오류→`error`, 짧은 동종 전문→`fallback`, 공통 필드 뒤의 잘못된 길이 접두부→`error`를 확인했다.

## 남은 규격 한계와 운영 해석

- **BC MS:** `bcc_ms`는 BC의 BCB/BCA/EPT 고정 레코드 형식에 부합한다. 5,776건의 `ok`는 업무 레코드 구조가 맞는다는 뜻이지, 업무 세부 필드의 추출 성공을 뜻하지 않는다. 공식 필드별 offset 근거가 없어 현재 `fields`는 비워 둔다. 7,680건의 제어전문은 `control`로 분리된다. `win_ms`는 바이트 단위로 동일한 중복 파일이므로 삼성 MS 검증에는 쓰지 않았다.
- **삼성 MS:** 진짜 삼성 MS 실로그가 없어서 프로필을 비활성으로 유지했다. 이 서비스의 정상 파싱은 검증하지 않았으며, 운영에선 `disabled`가 예상 결과다.
- **롯데 IC:** 제공된 `LTC_IC` 실로그의 본문은 첨부된 최신 IC 문서의 BCD/바이너리 레이아웃이 아니라 ASCII 고정 필드 형태다. 롯데 IC 전용 프로필로 이 **실제 로그 형태**만 검증했으며, 문서상의 바이너리 IC 전문은 검증되지 않았다. 롯데 MS와 별도 프로필로 유지한다.
- **농협 IC:** 특히 응답 `0110`·`0410`에서 127번 비트가 켜져도 문서상 요청 전용 길이 규칙을 그대로 적용하면 길이 접두부 오류가 대량 발생한다. 현 설정은 그 응답 필드를 무리하게 해석하지 않고, 남은 바이트가 있는 이벤트는 공통 필드와 `fallback`으로 보존한다. 실제 사례의 잔여 763바이트에는 공백뿐 아니라 비공백 데이터도 있어 무조건 패딩으로 버리거나 `ok`로 승격시키지 않았다. 이 구간의 확정적인 응답 레이아웃은 추가 규격 근거가 필요하다.
- **봉투 및 인코딩:** `] len[...]` 또는 `]`가 빠진 멀티라인/잘린 로그도 같은 프로필·공통 필드를 확인할 수 있으면 `fallback`으로 남긴다. 원문이 이미 U+FFFD 대체문자로 손실됐다면 RB만으로 복원할 수 없다.

## 운영 적용·최적화 검토

RB는 규격을 등록 시 1회 컴파일·freeze하고 이벤트마다 파일 I/O나 네트워크 호출을 하지 않는다. 본문 상한 65,536바이트, bitmap 최대 수, 가변 필드 길이, TLV 범위를 검증한다. 4개 워커의 최종 전체 재생은 279.262초(테스트 하네스 포함 약 4,130건/초)였으며, 이는 운영 장비의 성능 보증치가 아니다. 기존의 단일 Ruby 필터+JSON 규격 방식은 유지하고, 확인되지 않은 바이트를 임의로 소비하는 최적화는 넣지 않았다.

운영 배포에서는 RB·JSON을 같은 `CARD_PARSER_DIR`에 두고 파이프라인을 재시작해 `card_detail.parser_version=2026-10-18.final8`을 확인한다. Ruby 필터 블록 자체는 `path`와 `specs_path`만 사용해도 되지만, 앞단의 카드사별 `target_alias`, 멀티라인 합치기 및 `message` 원문 보존은 필수다. 이번 검증은 제공 로그의 결정적 재생이지, 실제 Filebeat/Beats 전달·운영 인코딩·경로 라우팅까지 포함한 종단 간 검증은 아니다.
