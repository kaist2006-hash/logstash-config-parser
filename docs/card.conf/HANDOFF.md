# 다른 채팅에서 이어가기 위한 작업 메모

## 요청과 현재 범위

Logstash/Elasticsearch 8.17.6. 운영 서버는 내부망. **원시 로그와 Ruby/JSON 규격으로 상세 파싱이 맞는지만 검증**하며 Beats/ES 연결·저장은 요청 범위가 아니다. BGF 코드를 그대로 따르라는 요청이 아니라 외부 rb/json 참조 구조를 card.conf에 추가하는 작업이다.

현재 배포한 것이 아니라, 사용자가 요청한 1차 GitHub 저장 시점이다. 로컬/운영 원본 파일을 덮어쓰거나 운영 ES를 변경하지 않았다.

## 현재 결과

- 국민 IC 302,191건: 끝까지 해석, 선택 필드/TLV 구조 오류 0. 그중 150,950건은 문서 길이/헤더 차이 경고. 경고를 없애 성공률을 꾸미지 않는다.
- 롯데 MS 51,766건: 정상 23,989, 부분 24,913, 초기 실패 2,864. F57/F61 정의가 없고 잘린 로그가 있다. **롯데 전체 검증 성공으로 표현하지 않는다.**
- 단일/4-thread 전체 상세 결과 동일. 실제 8.17.6 LogStash::Event 사용.
- 합성 계약 27개 통과. 별도 계산한 원시 28표본/455필드값 대조 통과.
- 14개 프로파일 중 kb_ic, lotte_ms만 상세 파싱 활성화. 나머지는 문서 초안/실로그 미검증으로 비활성화. BC 기존 라우팅 2개도 유지.

## 다음 작업

1. 롯데 운영 MS의 F57/F61이 있는 최신 규격과 온전한 전문을 받아 확인한다. 비트 번호만 보고 일반 ISO8583 길이를 추정해 대입하지 않는다.
2. 국민 F60의 byte 길이 차이, F55 확장 길이, 다른 ISO 헤더를 기관의 실제 운영 규격과 확인한다. 이 관측값은 JSON notes와 문서 상한 경고에 남아 있다.
3. 다른 기관 원시 로그가 오면 파일 경로/기관/IC-MS를 먼저 확인하고, 기존 alias를 바꾸지 않은 채 보류 필드와 거래별 변형부터 검증한다.
4. 하위 필드 확대가 필요하면 비민감 운영 필드부터 추가하고, 새 JSON과 최종 Ruby 조합으로 전체 로그/오류계약/멀티스레드 대조를 다시 실행한다.
5. 원시 파일은 이 저장소에 없으므로 이전 파일명만 보고 파일을 갖고 있다고 가정하지 않는다. 새 채팅에서는 원시/규격 파일을 다시 첨부받거나 접근 가능한 위치를 확인한다.

## 하지 않은 것/주의

- 이 저장소에 원시 로그, 운영 비밀번호, 내부 ES IP, 실제 전문을 포함한 golden fixture를 저장하지 않았다.
- 공개 conf는 CARD_ES_HOST_1/2/3 및 CARD_ES_PASSWORD가 필요하다. 원래 운영 URL은 사용자가 원본 conf에서 설정한다.
- JSON 변경은 자동 감지되지 않는다. register 시 읽으므로 적용에는 명시적인 pipeline 재시작/reload가 필요하다.
- 롯데 텍스트 전문에는 이진값이 포함될 수 있다. 이번 검증은 ISO-8859-1 byte-preserving 운반을 사용했다. 이미 U+FFFD로 손실된 message는 복구할 수 없다.
- 기존 message/a_header/b_body에 민감정보가 있을 수 있다. 추가 상세 파서는 민감 원문을 새 필드로 내보내지 않지만 기존 원문 마스킹까지 구현한 것은 아니다.
- 파서 코어 검증과 전체 Logstash 프로세스/외부 서비스 검증을 혼동하지 않는다. 업무 승인 성공 여부도 프레임 파싱 성공과 별개다.
