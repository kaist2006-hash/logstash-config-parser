# Filebeat multiline + Logstash 파싱 검증

검사일: 2026-10-23

## 검사 방법

첨부 실로그를 CP949로 읽고, Filebeat의 날짜·시간 시작 경계와 빈 줄 제외·include_lines를 Python에서 재현했습니다. 생성된 digital.conf의 실제 grok 패턴 두 개를 Python 정규식으로 대응시켜 요청 kv 상당 처리·응답 JSON 파싱을 검사했습니다. TR_ID 변환에는 실제 Java URLEncoder를 사용했습니다.

이전 구간 위치 기준으로 독립 추출한 요청·응답 전체 값과 비교했습니다. 아래 수치는 새로운 실제 Filebeat/Logstash 실행 결과가 아니라 오프라인 재현 결과입니다.

TR_ID 집합 비교는 첨부 전체 요청에 같은 값이 존재한다는 뜻입니다. 1:1 거래 결합 또는 중복 제거를 검증한 결과가 아닙니다.

## 별도 검사 14개

한 줄 배열, 다음 줄 닫는 대괄호, 중첩 배열·여러 줄 JSON, RESULT_CODE 없는 응답, CRLF, RESULT DATA 제외, 단독 JSON 제외, 단독 URL 제외, 일반 로그 제외, 잘못된 JSON 제외, 닫는 대괄호 누락 제외, 종료 구분선 누락 제외, query 없는 URL, 빈 query 값 보존을 확인했습니다.

완성 이벤트의 순서를 섞어도 결과가 같다는 검사는 새 필터가 이벤트 간 상태를 참조하지 않는다는 재현 확인입니다. 실제 Logstash 다중 worker 처리량·동시성 검사가 아닙니다.

## 정적 비교와 한계

- 기존 최신 GitHub 설정의 VAN 분기·후속 처리·input·output을 보존합니다.
- 접속 password는 임시값 00000000 네 곳입니다.
- aggregate·map 상태·Logstash 본문 조합 제거를 확인했습니다.
- 괄호·문자열 균형 검사를 통과했습니다. 실제 Logstash -t를 대신하지 않습니다.
- timeout 없이 완전한 레코드를 읽는 경우를 재현했습니다. 실제 줄 도착 간격, Filebeat timeout·registry·회전·재시작·입력 유형 이전은 검사 범위 밖입니다.
- Filebeat와 Logstash 실행 파일이 현재 작업 환경에 없어 제품 자체의 실행 검사는 수행하지 않았습니다.
- 제공 Filebeat 예시는 실제 운영 input·ID·path·encoding과 병합 후 검사해야 합니다.
